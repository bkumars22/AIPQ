How the real product actually works

AIPQ is five real services, not one app. The dashboard you've been looking at (aipq.chaitrishodaya.com) is a static, no-backend build made for GitHub Pages — everything below is the real thing, running locally.

The real flow, step by step

  1. You register a project once, via a dashboard login (JWT) — POST /projects/register. This mints a real, one-time-shown api_key for that project. Done for real today: ARIA (project 1) and QAIP (project 2).
  2. Your app calls @aipq_prompt(...) around the function that returns your system prompt text. Every time that text changes, the SDK POSTs a new version to the backend and blocks until it's scored.
  3. The backend hands the version to ai-engine for scoring — deterministic pattern checks first (forbidden/required text), then two real LLM-judge passes (faithfulness, compliance) via deepeval.
  4. A score ≥ your threshold deploys it, live, to the dashboard. A score below it raises PromptQualityError in your code — the bad prompt never reaches production.
  5. Once deployed, report_usage() streams real production outputs back for drift monitoring; ai-engine's scheduler re-checks deployed versions every 15 minutes and can flag CRITICAL drift, same as the real July 7 ARIA rollback you already have live.

Every real change made

Nine real edits across two codebases (this AIPQ repo, and the sibling SCIP ai-service), all found by actually running the system and reading real error output — not guessed in advance.

Fix · AIPQ · ai-engine/llm_judge.py, providers.py, validators/rag_validator.py

Deprecated Groq model name (3 files)

llama-3.3-70b-versatile → openai/gpt-oss-120b. Groq removed the old model; every call was 404'ing. This is the exact same bug already found and fixed once today in the sibling SCIP repo's bct/system_adapters.py — same root cause, different codebase.

Fix · AIPQ · ai-engine/evaluators/pipeline.py

uvloop / nest_asyncio incompatibility

Switched faithfulness_judge.measure() / compliance_judge.measure() (sync) to a_measure() (async). deepeval's sync path calls nest_asyncio.apply() to patch the running event loop — which cannot patch uvloop (the default loop under uvicorn[standard], which this service runs on) and raised ValueError on every single evaluation. The function was already async end-to-end, so awaiting the async method directly was the correct fix, not disabling uvloop service-wide.

Attempted, then reverted · AIPQ · ai-engine/llm_judge.py

Groq response_format=json_object

Tried as the standard fix for "judge LLM returned invalid JSON." Made things strictly worse — Groq's server-side json-mode validator now rejects deepeval's generated prompt outright (400 json_validate_failed) instead of returning malformed-but-present text. Reverted. See the open issue below — this is not resolved.

Add · AIPQ · backend/.dockerignore, ai-engine/.dockerignore, frontend/.dockerignore

Missing .dockerignore files

None existed anywhere in this repo. The first build attempt genuinely stalled for 35+ minutes transferring frontend/node_modules (158MB) and Python cache directories into the Docker build context on every build. Adding these cut a full rebuild from 35+ minutes (stalled) to under 2 minutes.

The one open bug — honestly, not glossed over

deepeval's GEval judge can't reliably get valid JSON out of Groq

Every version of both ARIA's and QAIP's real prompts ends FAILED with quality_score = null or 0.0 — this is not a real judgment that the prompts are bad. The deterministic and prompt-execution stages both genuinely run and succeed; the pipeline only fails at the LLM-judge scoring step, before a real score is ever produced.

Without response_format, the judge's raw text often isn't parseable JSON:

deepeval.metrics.utils.generation: ValueError: Evaluation LLM outputted an invalid JSON.
Please use a better evaluation model.

With response_format={"type": "json_object"} (the standard fix — tried and reverted), Groq's own server-side validator rejects the request before generation even starts:

groq.BadRequestError: Error code: 400 - {'error': {'message': "Failed to validate JSON.
Please adjust your prompt. See 'failed_generation' for more details.",
'code': 'json_validate_failed', 'failed_generation': ''}}

Both are real, reproducible, and documented in the code with a comment pointing here rather than silently left broken.

Next steps to actually close this out

  1. Fix the judge-JSON issue for real — likely candidates: a different judge model (an Anthropic or OpenAI key would sidestep Groq's json-mode quirks entirely), or a deepeval-side prompt adjustment so Groq's validator accepts it.
  2. Once a version actually DEPLOYS, it becomes visible on the real dashboard at localhost:3001 with a genuine, computed quality score — not before.
  3. The GitHub Pages demo site is unaffected — none of this touches aipq.chaitrishodaya.com, which stays exactly as it was (static, hardcoded ARIA/QAIP fixture data), since it's a separate, unconnected build.
